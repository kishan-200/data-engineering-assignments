# Smart Meter Energy Monitoring

## 1. Project Overview

The **Smart Meter Energy Monitoring System** is a real-time data engineering project that processes electricity consumption readings generated by smart meters.

The system collects smart meter events, sends them to **Apache Kafka**, processes the streaming data using **Apache Spark Structured Streaming**, validates the incoming events, calculates customer-level energy consumption using time windows, detects abnormal consumption, and stores the processed data in **HDFS** for historical analysis.

**Hive** is used for analytical queries on the processed data, while **HBase** is designed to maintain the current state of individual smart meters for fast lookup.

The project demonstrates an end-to-end streaming data pipeline involving:

- Scala
- Apache Kafka
- Kafka partitions
- Consumer groups
- Kafka offsets
- Spark Structured Streaming
- Windowing
- Watermarking
- Checkpointing
- HDFS
- Hive
- HBase
- Fault-tolerance concepts
- Data validation
- Abnormal consumption detection

---

## 2. Problem Statement

Smart meters continuously generate electricity consumption readings.

Each reading contains information such as:

- Meter ID
- Customer ID
- Electricity consumption
- Timestamp

The system must process these readings in real time and provide:

1. Continuous ingestion of meter readings
2. Validation of incoming events
3. Window-based consumption calculations
4. Customer-level aggregation
5. Detection of unusual consumption
6. Historical storage
7. Analytical querying
8. Current-state storage
9. Checkpoint-based recovery
10. Fault-tolerance demonstration

---

## 3. Objectives

The main objectives of the project are:

- Generate smart meter events using Scala.
- Publish events to a Kafka topic.

# 6. Smart Meter Event Schema

Each smart meter event is represented as JSON.

Example:

```json
{
  "meter_id": "M1001",
  "customer_id": "C101",
  "units": 21.17,
  "timestamp": "2026-09-22 16:49:52"
}
```

### Fields

| Field | Description |
|---|---|
| `meter_id` | Unique smart meter identifier |
| `customer_id` | Customer associated with the meter |
| `units` | Electricity consumption reading |
| `timestamp` | Time at which the reading was generated |

# 7. Kafka Configuration



# 10. Consumer Groups and Offsets

Kafka consumer groups are used to manage message consumption.

A consumer group allows multiple consumers to work together while Kafka maintains offsets for the messages processed by the group.

Offsets represent the position of a consumer within a Kafka partition.

Example:

```text
Partition 0 -> Offset 120
Partition 1 -> Offset 135
Partition 2 -> Offset 110
```

If a consumer restarts, it can continue processing from its stored offset.

Consumer group information can be inspected using Kafka CLI commands.

# 12. JSON Parsing

Spark reads the Kafka message value as a string.

The JSON data is then converted into structured columns:

```text
meter_id
customer_id
units
timestamp
```

The timestamp is converted into a Spark timestamp column:

```text
event_time
```

This allows Spark to perform time-based window operations.

# 13. Data Validation

The streaming application validates every incoming reading.

The following conditions are checked:

- Missing `meter_id`
- Missing `customer_id`
- Missing or invalid `units`
- Negative consumption values
- Invalid timestamp
- Invalid JSON

Example:

```text
meter_id = null
```

Result:

```text
INVALID
```

Example:

```text
units = -10
```

Result:

```text
INVALID
```

Valid records are allowed to continue through the streaming pipeline.

Invalid records are separated and displayed for validation monitoring.

---

# 14. Validation Status

Each event receives a validation status:

```text
VALID
```

or

```text
INVALID
```

An error reason is also generated.

Example:

```text
validation_status = INVALID
error_reason = Negative units
```

Another example:

```text
validation_status = INVALID
error_reason = Missing meter_id
```

This makes the pipeline easier to debug and monitor.

---

# 15. Windowing

The project uses a **1-minute tumbling window**.

```text
Window Duration = 1 minute
```

Example:

```text
10:00:00 - 10:01:00
10:01:00 - 10:02:00
10:02:00 - 10:03:00
```

Within each window, Spark calculates customer-level consumption.

---

# 16. Watermarking

A watermark of:

```text
30 seconds
```

is used.

```text
Watermark = 30 seconds
```

Watermarking allows Spark to handle events that arrive late while preventing the streaming state from growing indefinitely.

The streaming pipeline uses:

```scala
.withWatermark("event_time", "30 seconds")
```

# 17. Customer-Level Consumption

For every customer and time window, the application calculates:

- Total consumption
- Average consumption
- Peak consumption
- Number of readings

Example:

```text
Customer: C101

Total Units: 35.68
Average Units: 17.84
Peak Units: 21.17
Reading Count: 2
```

# 18. Abnormal Consumption Detection

The system identifies unusual consumption using the peak reading.

The project uses the following rule:

```text
peak_units > 20
```

If the condition is true:

```text
ABNORMAL
```

Otherwise:

```text
NORMAL
```

Example:

```text
Customer: C101
Peak Units: 21.17
Status: ABNORMAL
```

Example:

```text
Customer: C104
Peak Units: 9.39
Status: NORMAL
```

# 19. Spark Checkpointing

Checkpointing is used to maintain streaming state and progress information.

The project uses separate checkpoint locations for the streaming queries.

Example:

```text
/tmp/smart-meter-consumption-checkpoint-v2
```

and:

```text
/tmp/smart-meter-validation-checkpoint-v2
```

The HDFS output query uses:

```text
/tmp/smart-meter-hdfs-checkpoint-v2
```

Checkpoint directories contain information such as:

```text
sources/
commits/
offsets/
metadata
```

This allows Spark to recover streaming progress after a failure or restart.

# 28. Kafka Fault Tolerance

Kafka provides fault tolerance through:

- Partitions
- Replication
- Leaders
- Followers
- In-Sync Replicas
- Consumer offsets

The current local project uses:

```text
Replication Factor = 1
```

because the local environment uses a single Kafka broker.

Therefore, there is no replica failover in the current setup.

The project demonstrates Kafka recovery by restarting the local Kafka service and verifying that the topic becomes available again.

For a production multi-broker deployment, replication would normally be configured with multiple brokers.

---

# 29. Spark Fault Tolerance

Spark Structured Streaming uses checkpointing to maintain processing progress.

The checkpoint stores:

```text
Source offsets
Commit information
Streaming metadata
State information
```

After restarting the streaming application, Spark can use the checkpoint to recover its streaming progress.

This demonstrates the fault-tolerance mechanism of Spark Structured Streaming.

# 30. Handling Failure Scenarios

The project considers the following failure and invalid-data scenarios:

| Scenario | Handling |
|---|---|
| Missing meter ID | Mark event INVALID |
| Missing customer ID | Mark event INVALID |
| Null units | Mark event INVALID |
| Negative units | Mark event INVALID |
| Invalid timestamp | Mark event INVALID |
| Invalid JSON | Mark event INVALID |
| Late event | Handled using watermark |
| Spark restart | Checkpoint recovery |
| Kafka restart | Topic and broker recovery |
| Duplicate events | Considered as a data-quality case |
| Out-of-order events | Handled through event-time processing and watermarking |

# 36. Important Design Decisions

## Kafka

Kafka is used as the streaming ingestion layer because smart meter events are continuously generated.

## Spark Structured Streaming

Spark is used for real-time processing, validation, event-time processing, windowing and aggregation.

## HDFS

HDFS is used for historical storage of raw and processed smart meter data.

## Hive

Hive provides SQL-based analytical access to processed Parquet data.

## HBase

HBase is designed for fast access to the latest state of individual meters.

## Checkpointing

Spark checkpointing maintains streaming progress and supports recovery.

The **Smart Meter Energy Monitoring** project implements an end-to-end streaming data engineering pipeline.

Smart meter readings are generated using Scala and published to Kafka. Kafka provides partitioned event ingestion, while Spark Structured Streaming processes the events in real time.

The Spark application validates incoming data, handles invalid readings, applies event-time processing, uses watermarking, performs one-minute window aggregation, calculates customer-level consumption and identifies abnormal consumption.

Processed data is stored in HDFS using Parquet and exposed through Hive for analytical queries. HBase is designed to maintain the current state of individual smart meters.

Checkpointing and recovery mechanisms demonstrate how the streaming application can maintain processing progress during failures.

Overall, the project demonstrates the integration of **Scala, Kafka, Spark Structured Streaming, HDFS, Hive and HBase** into a complete smart-meter streaming data engineering solution.
